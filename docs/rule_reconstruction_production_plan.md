# 규칙 복원 퍼즐 실제 게임화 계획

## 목적

현재 프로젝트는 핵심 규칙 복원 루프를 검증하는 프로토타입이다.

```text
규칙 조립 -> 테스트 실행 -> 목표 보드와 비교 -> 클리어 또는 오답
```

다음 목표는 이 구조를 실제 게임 프로젝트 수준으로 올리는 것이다.

핵심은 기능을 많이 붙이는 것이 아니라, 콘텐츠를 안정적으로 만들고 수정할 수 있는 구조를 먼저 갖추는 것이다.

## 전환 원칙

- 프로토타입 전용 코드를 줄인다.
- 스테이지는 코드가 아니라 데이터로 만든다.
- UI는 코드 생성보다 씬/프리팹 기반으로 안정화한다.
- 테스트는 게임 규칙과 상태 전이를 검증한다.
- 기획 데이터는 테스트로 고정하지 않는다.
- 스테이지 품질 검사는 실패 테스트가 아니라 에디터 리포트로 제공한다.

## M0. 프로토타입 기반 정리

목표:

현재 동작을 유지한 상태로 구조를 실제 게임용으로 정리한다.

작업:

- `RuleReconstructionPrototype` 역할 축소 또는 이름 변경
- 런타임 로직과 UI 바인딩 분리
- 임시 코드 생성 UI 제거
- 씬/프리팹 기반 UI로 전환
- 현재 룰 조립, 보드 표시, 테스트 실행 흐름 유지

완료 기준:

- 기존 플레이 루프가 동일하게 동작한다.
- UI가 모바일 가로 화면에서 깨지지 않는다.
- Presentation 코드가 화면 생성과 게임 상태 처리를 과하게 동시에 맡지 않는다.

## M1. 스테이지 데이터 파이프라인

목표:

코드 수정 없이 스테이지를 추가하고 수정할 수 있게 만든다.

작업:

- `PrototypeStageFactory` 의존 축소
- `StageAsset` 기반 스테이지 제작 흐름 확정
- Resources 또는 Addressables 로딩 정책 결정
- 스테이지 제작용 에디터 도구 추가
- 스테이지 분석 리포트 추가

분석 리포트 항목:

- 색상 수
- source 개수
- 겹침 정도
- 목표 보드 밀도
- 빈 보드 여부
- 과밀 보드 여부
- 유사 해답 수
- 예상 난이도

완료 기준:

- 새 스테이지를 에셋으로 만들 수 있다.
- 런타임은 에셋에서 스테이지를 로드한다.
- 스테이지 품질 문제는 테스트 실패가 아니라 리포트로 확인한다.

## M2. 게임 진행 구조

목표:

한 판 테스트가 아니라 연속 플레이 가능한 게임 흐름을 만든다.

작업:

- 스테이지 선택 화면
- 스테이지 해금 상태
- 클리어 상태 저장
- 현재 진행 저장
- 리셋, 다음 스테이지, 다시 플레이 흐름 정리
- 세션 상태와 저장 데이터 분리

완료 기준:

- 게임을 껐다 켜도 클리어 상태가 유지된다.
- 스테이지 클리어 후 자연스럽게 다음 스테이지로 이동할 수 있다.
- 저장 로직이 UI 코드에 섞이지 않는다.

## M3. 룰 조립 UX 완성

목표:

룰을 버튼으로 고르는 UI가 아니라, 퍼즐 부품을 조립하는 UI로 만든다.

작업:

- 색상 슬롯
- 방향 슬롯
- 범위 슬롯
- 효과 슬롯
- 블록 트레이 정리
- 선택한 블록과 장착된 슬롯의 연결감 강화
- 클릭 장착 또는 드래그 앤 드롭 중 하나로 조작 방식 확정
- 모바일 가로 기준 레이아웃 고정

완료 기준:

- 텍스트를 읽지 않아도 룰 구성을 대략 이해할 수 있다.
- 현재 선택 중인 룰과 블록이 명확하다.
- 작은 화면에서도 슬롯과 보드가 겹치지 않는다.

## M4. 플레이 피드백 개선

목표:

플레이어가 테스트 결과를 보고 다음 가설을 세울 수 있게 만든다.

작업:

- 테스트 실행 중 source 적용 표시
- 영향받는 칸 강조
- 숫자 변화 애니메이션
- 오답 칸 표시
- Target 복귀 버튼 또는 상태 표시
- Clear/Fail 연출 분리

완료 기준:

- 실패 후에도 결과 보드를 충분히 확인할 수 있다.
- 틀린 칸이 어디인지 명확하다.
- 클리어 여부가 즉시 이해된다.

## M5. 콘텐츠 확장

목표:

게임 볼륨을 늘릴 수 있는 스테이지 팩 구조를 만든다.

추천 팩:

- 튜토리얼 팩
- 기본 팩
- 응용 팩
- 고난도 팩

작업:

- 팩 단위 스테이지 그룹
- 난이도 태그
- 사용 가능한 블록 제한
- 스테이지 순서 관리
- 기획용 스테이지 메모 필드

완료 기준:

- 팩 단위로 스테이지를 관리할 수 있다.
- 특정 팩만 빌드하거나 테스트할 수 있다.
- 스테이지 순서 변경이 코드 수정 없이 가능하다.

## M6. 실제 게임 품질

목표:

배포 가능한 기본 품질을 만든다.

작업:

- 타이틀 화면
- 옵션 화면
- 볼륨 설정
- 사운드
- 간단한 전환 애니메이션
- 해상도 대응
- 빌드 설정 정리
- 플랫폼별 입력 확인

완료 기준:

- 시작부터 종료까지 게임 흐름이 끊기지 않는다.
- 기본 사운드와 피드백이 있다.
- 대상 해상도에서 UI가 깨지지 않는다.
- 배포 빌드를 만들 수 있다.

## 테스트 기준

테스트로 강제할 항목:

- 룰 시뮬레이션
- source cell 제외 정책
- 보드 검증 정책
- 세션 상태 전이
- 저장과 로드
- `StageAsset` 변환

테스트로 강제하지 않을 항목:

- 특정 스테이지의 정답
- 특정 스테이지 순서
- 유일해답 여부
- 난이도 판단
- 기획 의도

스테이지 품질은 테스트가 아니라 에디터 분석 리포트로 관리한다.

## 우선순위

가장 먼저 진행할 작업은 M0이다.

추천 순서:

1. `RuleReconstructionPrototype` 역할 분해
2. 씬/프리팹 기반 UI 구조 정리
3. 런타임 세션과 UI 바인딩 분리
4. 기존 플레이 흐름 유지 확인
5. 이후 `StageAsset` 제작 파이프라인으로 이동

이 순서로 가야 이후 드래그 슬롯, 스테이지 선택, 저장 구조를 얹어도 UI와 로직이 다시 무너지지 않는다.
